# 복합 인덱스 효과 측정 — CommercialData (통합카테고리, 기준_년분기_코드)

마이그레이션 `0010_commercialdata_category_quarter_idx`로 추가한 복합 인덱스가 조회 시간을 얼마나 줄이는지 측정한 기록이다.
스크립트는 [`scripts/measure_index.sql`](../scripts/measure_index.sql), 원본 출력은 [`docs/index_measurement/`](index_measurement/)에 있다.

## 대상 쿼리

추천·적합도 점수에서 정규화 기준값(전체 행정동의 최댓값)을 구할 때 쓰는 업종 × 최신 분기 조회다(`backend/analysis/views.py`).

```sql
SELECT "총유동인구", "점포수", "업종_포화도"
FROM analysis_commercialdata
WHERE "통합카테고리" = :업종 AND "기준_년분기_코드" = :최신분기;
```

## 환경

| 항목 | 값 |
|---|---|
| DBMS | PostgreSQL 14.22 (Homebrew), Apple Silicon 맥 로컬 |
| 테이블 | `analysis_commercialdata` 408,576행, 265MB |
| 최신 분기(20253) 행 수 | 15,076행 (업종 51개) |
| 설정 | shared_buffers 128MB, work_mem 4MB, random_page_cost 4, jit on (모두 기본값) |
| 측정일 | 2026-11-17 (2회), 참고로 2026-10-13 1회 |

## 방법

- 조건 4가지마다 **51개 업종 × 5회 = 255회**를 `EXPLAIN (ANALYZE)`로 실행해 Execution Time을 모았다. 업종마다 1회 예열한 뒤 측정했다.
- 인덱스 추가·삭제는 `BEGIN … ROLLBACK` 안에서만 했다. 측정 전후 인덱스 목록이 같다는 것을 출력으로 확인했다.
- 조건마다 실제로 쓰인 실행계획 노드와 인덱스 이름을 함께 기록했다.

| 조건 | 인덱스 상태 |
|---|---|
| A | 기존 인덱스 4개만 — (행정동명), (행정동명, 분기), (분기), (행정동명, 통합카테고리) |
| B | A + 복합 인덱스 (통합카테고리, 분기) |
| C | 보조 인덱스 없음(기본키만) |
| D | 복합 인덱스만 |

## 결과

실행 시간(ms), 255회 기준.

| 조건 | 1차 평균 | 1차 중앙값 | 2차 평균 | 2차 중앙값 | 2026-10-13 평균 | 실행계획 |
|---|---:|---:|---:|---:|---:|---|
| A 기존 인덱스 | 0.964 | 0.966 | 1.055 | 0.962 | 0.964 | 분기 인덱스 Index Scan 후 업종 필터 |
| B 기존 + 복합 | 0.145 | 0.121 | 0.084 | 0.094 | 0.088 | 복합 인덱스 Bitmap Index Scan |
| C 보조 인덱스 없음 | 25.711 | 24.740 | 24.356 | 24.263 | 25.476 | 병렬 Seq Scan |
| D 복합만 | 0.093 | 0.100 | 0.083 | 0.093 | 0.094 | 복합 인덱스 Bitmap Index Scan |

읽은 페이지 수(카페 업종 실행계획, 2차): A 1,268페이지 → B 424페이지. A는 최신 분기 15,076행을 인덱스로 찾은 뒤 14,655행을 필터로 버리고, B는 필요한 421행만 찾는다.

## 해석

- 기존 인덱스가 있는 상태(A)에서 복합 인덱스를 추가하면(B) 조회 시간이 **약 0.96ms에서 약 0.1ms로** 줄었다. 배수로는 측정에 따라 **약 7~13배**다(평균 기준 6.6~12.6배, 중앙값 기준 8~10배).
- 0.1ms 수준의 시간은 실행할 때마다 흔들린다. 1차 측정의 B는 255회 중 1회가 5.1ms로 튀어 평균(0.145ms)이 중앙값(0.121ms)보다 높게 나왔다. 그래서 한 번의 평균값이 아니라 범위로 적는다.
- 읽은 페이지 수는 실행마다 흔들리지 않는다. 같은 조회에서 A는 B의 약 3배를 읽는다.
- 보조 인덱스가 전혀 없는 상태(C)와 비교하면 차이가 훨씬 크지만(약 25ms), 실제 서비스에는 기존 인덱스가 있었으므로 **개선 효과의 기준은 A**로 둔다.

## 한계

- 맥 한 대의 로컬 DB, 캐시가 채워진 상태(warm)에서 잰 값이다. 동시 요청이 있거나 캐시가 비어 있는 상황은 측정하지 않았다.
- 조회 한 번의 절대 시간이 1ms 안팎이라, 이 인덱스가 화면 응답 시간에 주는 영향은 작다. 이 기록은 ‘인덱스가 실행계획과 읽기 양을 어떻게 바꾸는가’를 확인한 것이다.
- 쓰기 비용(인덱스가 하나 늘어난 데 따른 적재 시간·저장 공간 증가)은 측정하지 않았다.
- 1차 측정은 실행계획 예시에 ‘최신 분기 찾기’ 서브쿼리가 들어간 초기 스크립트로 실행했다(D 예시의 9.8ms는 그 서브쿼리 시간). 255회 측정값은 두 버전 모두 같은 방식(분기 값을 리터럴로 넣은 쿼리)이며, 현재 스크립트는 예시도 같은 조건으로 맞췄다.
- 2026-10-13 값은 같은 방식으로 잰 것이지만 당시 출력 파일은 남아 있지 않다.
